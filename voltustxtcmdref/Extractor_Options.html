Extractor Commands


black_macros

Syntax


black_macros file filename

Description

Note: This is equivalent to the command cell black - which is now the preferred command.

The black_macros command excludes the contents of selected macros from the gray data during graybox extraction. Use this command when you want zx to ignore the effect of large megacells that reside under areas of the routing layer that contain no routing.

Arguments

file filename

Specifies the name of the file that lists the macros to consider as black boxes during graybox extraction. In the file, specify one macro per line.

Examples

Consider a file called black.box whose contents are the following. Each line is an instance of the macro to be ignored.

P20

P30

P60

P70

In the following example, zx ignores the contents of all instances of the P20, P30, P60, and P70 macros listed in the black.box file during graybox extraction:

black_macros file black.box

cell black

Syntax


cell black cell_name

Description

The cell black command is used to ignore gray data information from the named cell. Functionally equivalent to the QXC V3.x command black_macros.

Arguments

cell_name

Specifies the name of the cell.

Examples

The following example specifies that zx is to ignore the gray data information for all instances of the `NAND2X' and `iobufx' cells.

cell black NAND2X

cell black iobufx

cell ignore

Syntax


cell ignore cell_name

Description

The cell ignore command is used to exclude all references to the named cell from the design database. Functionally equivalent to the QXC 3.x command ignore_macros.

Arguments

cell_name

Specifies the name of the cell.

Example

The following example specifies that zx is to exclude all references to the `AND3X' cell:

cell ignore AND3X


cell_ignore_file

Syntax


cell_ignore_file filename

Description

Excludes all references to the named cells in the specified file, from the design database


Arguments

filename

Specifies the filename containing the list of cells to be ignored.


cell map

Syntax


cell map from_cell to_cell

Description

Used to resolve conflicts between names in the design database and names used in the library. One usage is to force design cell names to correspond to library names - this is a more common problem in GDS2 designs where uppercase cell names do not match lowercase library names. Another usage is to change a design cell that is not intended to be mapped to a library view.

Arguments

from_cell

Specifies the source cell name.

to_cell

Specifies the target cell name.

Examples

cell map NAND2X nand2x

cell map iobuf iobufx


cluster distance

Syntax


cluster distance layer_name distance max_dimension

Description

Specifies how to cluster or re-cluster via arrays. Since the clustering approach reduces the RC elements by clustering vias into one node, it can boost the IR drop analysis runtime in dynamic mode.

Arguments


layer_name

Specifies the name of the via layer.

distance

Specifies that all via geometries on the specified via layer within distance , in microns, of other via geometries will be clustered together into a multi-cut via.

max_dimension

Specifies that if the resulting cluster exceeds the max_dimension in either number of rows or columns of vias it will be split in half repeatedly until the maximum number of rows or columns, per cluster, is less than or equal to the max_dimension .

Examples

This example specifies that all via1 geometries within 1 micron distance from each other will be clustered. The maximum cluster size in either x or y direction is 4 vias.

cluster distance via1 1.0 4

density_check_rectangle

Syntax


density_check_rectangle x1 y1 x2 y2

Description

The density_check_rectangle command checks wire density in a specified area of the chip.

Note: This command must be used with the variable density_check_method, set to rectangle.

Arguments

x1 y1 x2 y2

The two sets of X and Y coordinates represent the leftmost, bottommost point of the area to be checked and the rightmost, topmost point, in microns.

Examples

The following example checks the wire density in a rectangular area defined by 0,0 and 500, 500:

setvar density_check_method rectangle

density_check_rectangle 0 0 500 500

extraction_type

Syntax


extraction_type [all|special|regular|mustjoin| file filename |pattern pattern ] [ extraction_type | capacitance_type ]

Description

The extraction_type command controls the type of extraction performed on the nets and selects the nets on which to perform the extraction. By default, Fire & Ice QX extracts all regular nets as a decoupled RC network.

Arguments


all

Extracts all nets.

file filename

Extracts all nets listed in the filename file.

Note: f you select this option, you should first turn off the default value by setting the all option to none, as in the following example, unless you want to extract in two different modes, such as coupled and decoupled:


extraction_type all none


extraction_type file gamma decoupled_rc

pattern pattern

Selects all nets whose names contain the pattern specified by pattern . pattern uses the DEF regular expression syntax, which follows:

*

Matches any sequence of 0 or more characters. For example, *net* matches 123netxyz, netvdd, and 10ce463pnet.

%

Matches any single character.

For example, bus% matches bus1, bus2, bus3, and so forth. Similarly, clock%test matches clock7test, clock8test, and clock9test, but not clock10test.

-

Matches the whole sequence of characters up to and including the next period ("."). If there is no "." in the string, it matches to the end of the string.

For example, --bus3 matches bus3 in the following expression: block1.cell2.bus3

extraction_type

Specifies the type of RC extraction. The type of RC extraction can be one of the following:

r_only

Extracts only the resistance.

decoupled_rc

Extracts the decoupled resistance and capacitance network. This option is the default.

none

Performs no extraction on the defined set of nets.



capacitance_type

Specifies the type of capacitance extracted. The type of capacitance extraction can be one of the following:

total_c

Extracts the total capacitance.

none

Extracts no capacitance.

Note: There is no limit to the number of extraction_type commands that you can define in a single command file, so you can use them repeatedly to fully describe the nets to extract and completely control the extraction. Later specifications override earlier ones if they select the same nets.

Note: By default, zx extracts all regular nets as a decoupled RC network. Reduction of the output is controlled by the reduce_output variable.

Note: zx detects power and ground nets from the DEF file by their +USE POWER and +USE GROUND attributes. It excludes these nets from the extraction unless you explicitly request that they be extracted by using their name or a matching pattern with the extraction_type command.

Examples

Example 1

The following example performs resistance-only extraction on all nets:

extraction_type all r_only

Example 2

This example extracts the decoupled resistance and capacitance on all regular nets:

extraction_type regular decoupled_rc

Example 3

This example performs no extraction on the nets listed in the exclude.nets file:

extraction_type file exclude.nets none

Example 4

This example extracts decoupled resistance and capacitance from all nets containing the clk* pattern:

extraction_type pattern clk*

Example 5

This example shows that If the file option is selected, the default value must first be turned off by setting the all option to none:

extraction_type all none

extraction_type file gamma decoupled_rc

Example 6

The following example shows how to extract only a design's signal nets by excluding the extraction of the power nets:

extraction_type all decoupled_rc

extraction_type pattern *VDD none

 

ignore_macros

Syntax

ignore_macros file filename

Description

Note: This is equivalent to the command cell ignore, which is now the preferred command.

The ignore_macros command excludes certain macros, also known as cells, from the zx resistance and capacitance extraction. If a net refers to a pin of an excluded macro, zx excludes that pin as well. It does not generate warnings or errors pertaining to excluded macros.

Arguments


filename

Specifies the name of the file that lists the macros to ignore during extraction. In the file, specify one macro per line.


Examples

The following example ignores all instances of the logo_cell, top_right, top_left, bottom_right, and bottom_left macros, which are listed in the ignore.cells file:

ignore_macros file ignore.cells

 

ignore_pin

Syntax


ignore_pin pin_name

Description

Note: This is equivalent to the command pin ignore, which is now the preferred command.

The ignore_pin command allows you to specify certain instance ports, such as the power and ground ports, which are not extracted for timing when zx generates the CeltIC NDC database.

Arguments

pin_name

Specifies the pin name adhering to the DEF regular-expression rules for pin names. You can specify more pins by repeating the ignore_pin command. See example 2 below.


Examples

Example 1

In the following example, zx ignores pins with a pin name of VDD during generation of the CeltIC NDC database:

ignore_pin VD

Example 2

In the following example, multiple pins are specified to be ignored:

ignore_pin VDD

ignore_pin VSS

ignore_pin GND

include_via_res_table_file

Syntax

include_via_res_table_file filename

Description

The include _via_res_table_file is used for defining different resistances for different sized vias.

Arguments

filename

Name of the file that defines the resistances for various sized vias.

File syntax:

via pro_layer = " via_name " <ext_layer = " layer_name "> < res_value> [ area [ res_value area ] ...]

where:

pro_layer via_name

Refers to the via name specified in the ict file.

ext_layer layer_name

Refers to the extraction layer, and is optional.

res_value

Defines the resistance value in ohms.

area

Defines the area. Units are in 1.0e-06 square microns

Ext_layer refers to your def layer name and it is optional. Pro_layer must be specified first (after via command), before ext_layer and area settings.

For via area entries not specified in the table, ZX does as follows.

  • Use linear interpolation, if the via area is falling in between area values specified.
  • Use boundary values, if the area value is out of range.

Examples

The following example defines the via_res_table_file file as via_res:

include_via_Res_table_file /users/eng/test/via_res

The file would look something like this:

via pro_layer = "via2" ext_layer = "via23" 1.0 8100 0.75 14400


label net

Syntax


label net label x y layer_name <cell_name>

Description

The label net command is used to annotate (transfer) a net name to a geometry on the given layer enclosing the given x,y coordinates. If the cell name is given, the x,y coordinates are in reference to the coordinates of the cell.

Note: This takes precedence over GDS text annotation.

Arguments

label

Specifies the net names.

layer_name

Specifies the name of the layer.

x y

Specifies the enclosing coordinates specified in microns.

cell_name

Specifies an optional cell-name

Examples

The following example specifies that zx is to annotate the IN1 label to the 500 500 coordinates of the metal1 layer:

label net IN1 500 500 metal1

Syntax


label port label x y layer_name <cell_name>

Description

The label port command is used to create a pin object with the label name on the given layer at the x,y location. If the cell name is given, the x,y coordinates are in reference to the coordinates of the cell.

Arguments

label

Specifies the net name.

layer_name

Specifies the name of the layer.

x y

Specifies the enclosing coordinates specified in microns.

cell_name

Specifies an optional cell name

Examples

The following example specifies that zx is to create a pin object with a XYZ1 label on the metal2 layer at the 7500 8500 coordinates:

label port XYZ1 7500 8500 metal2

layer

Syntax

layer layer_name [<icecaps icecaps_layername >|<gds layerID datatype >]

Description

Note: This is equivalent to the new commands "layer map", and "layer gds", which are now the preferred commands.

The layer command maps the layer names in the LEF technology file to the layer names in the IceCaps technology file or the GDSII file used to import metal fill. You only need to use this command if the layer names specified in the IceCaps technology file or the GDSII file are different from those used in the LEF file.

Arguments

layer_name

Specifies the name of the layer in the LEF file.

icecaps icecaps_layername

Maps between a layer in the LEF file and a layer in the IceCaps technology file or the RCgen technology file.

gds

Maps between a layer in the LEF file and the GDSII file.

layerID

Specifies the layer number of the GDSII layer.

datatype

Specifies the number of the subclass for the GDSII layer. If you do not specify a data type, zx uses all data types for that GDSII layer.

Examples

The following example maps the METAL1 layer in the LEF file to layer 4 in the GDSII file:

layer METAL1 gds 4

layer bias

Syntax

layer bias layer bias_value [r_only|c_only|both]

Description

The layer bias command sets a bias value, in microns, by which to undersize all wires on a defined layer. It must be in the range of -1 to 1. This value is applied to each edge of the wire, decreasing the width by two times the bias value. The biasing changes only the width of the wire, not the length. You can select a different bias value for resistance extraction and capacitance extraction.

Arguments

layer

Specifies the name of the layer containing the wires to be biased.

bias_value

Specifies the amount, in microns, by which to bias the wires. A positive value undersizes the width of the wire.

r_only

Applies the bias value only during resistance extraction.

c_only

Applies the bias value only during capacitance extraction.

both

Applies the bias value during both resistance and capacitance extraction.


Examples

The following example decreases each edge of the wires in metal5 by one tenth of a micron during resistance extraction, and by two tenths of a micron during capacitance extraction:

layer bias m5 0.1 r_only

layer bias m5 0.2 c_only

The results will resemble the following diagram:

layer gds

Syntax


layer gds layer_name gds_layer_num < gds_datatype_num < gds_datatype_range >> [port| text | net | fill | slot]

Description

This command associates a layer_name with the integer layer value gds_layer_num found in the GDS2 data. This layer name comes from the extraction technology file.

All layers in GDS2 format, to be used for extraction, must be defined with the layer gds command. Multiple commands may use the same layer_name in order to combine data in GDS2 with different layer or datatype fields into a single extraction layer.

The GDS2 format defines legal values for both layers and datatypes as 0 to 255 inclusive. Any combination of layer gds statements may be used with these values for layer and datatype. Omission of any datatype information implies that all datatypes for that layer are used. Single values and ranges for datatypes may also be specified for each layer gds statement.

Arguments


layer_name

Specifies the name of the layer

gds_layer_num

Specifies the GDS layer number

gds_datatype_num

Specifies an optional single gds2 datatype number, or the first datatype number for when a range is specified

gds_datatype_range

Specifies a gds2 datatype range, specified as a third number.

port

Keyword used to include GDS2 text objects (all texttypes) as port definitions for the layer

net

Keyword used to transfer text from GDS2 text objects (all texttypes) as a net name annotation to the geometry enclosing the text location. There is no difference between the port and net keywords - they are duplicated in order to get consistent terminology with the label net command.

text

Keyword indicating that all GDS2 text on the given layer is to be read (including all texttypes) and interpreted as labels

fill

Keyword indicating that geometries with the given layer/datatype values are to be considered to be explicit fill data

slot

Keyword indicating that geometries with the given layer/datatype values are to be considered as explicit slotting data

Examples

Example 1

The extraction technology file contains information for a layer called MET1. The information for this layer is read from the GDS2 file on integer layer 8. The corresponding command file would contain the following:

layer gds MET1 8

This single statement would be sufficient to get data from this layer in the GDS2 to the extractor on the MET1 layer. The data used for this layer includes all polygons and paths (of all pathtypes). If the technology file was changed to use METAL1 as the layer name instead of MET1, then in the command file you could either change the layer gds command or add an additional layer map command:

layer gds MET1 8

layer map MET1 METAL1

The layer map command can also be used to associate DEF layer names to technology layer names when they do not match.

Example 2

Any number of layer gds commands may be used. Multiple statements with the same layer_name have the effect of combining data.

layer gds MET1 8

layer gds MET1 14

This example combines data from GDS2 layers 8 and 14 into a single extraction layer named MET1.

Example 3

To specify a range of datatypes for a particular layer, you enter the beginning and ending datatype numbers.

layer gds MET1 8 2 7

This command associates GDS layer number 8 with the layer name MET1, for all data types numbered 2 to 7.

layer map

Syntax


layer map layer_name tch_layer_name

Description

The layer map command is used to map a layer_name to a layer defined in the technology file. Layers with names that match technology layer names are mapped implicitly. Design layers may be excluded from extraction by mapping the layer_name to a name not defined in the technology file.

Arguments


layer_name

Name of the layer

tch_layer_name

Name of the layer defined in the technology file

Examples

layer map METAL_8 dummy_METAL_8

Note: This example will discard data on METAL_8 from extraction.

promote_ports

Syntax


promote_ports [none | all | cell cell_name pin pin_name | inst inst_name pin pin_name ]

Description

The promote_ports command is used to control the use of port geometries during extraction.

Arguments

none

The default value. Also, this is the default if no promote_ports command is found. This means that all port geometry will be subtracted from interconnect geometry and will not be used to generate parasitic values. This option will ensure that no cell parasitic is included in the interconnect model, but it could cause errors with respect to feedthru resistance or coupling capacitance to ports.

all

The all option merges all of the port geometries into the interconnect. This provides more accurate feedthru resistance and coupling capacitance, but could duplicate some parasitic effects included in the library model.

cell

The cell cell_name pin pin_name specification is used to selectively include the port geometry of a specific pin from all instances of a cell.

inst

The inst inst_name pin pin_name specification is used to selectively include the port geometry of a specific pin from a single instance.

pin_name

Specifies the specific cell or instance pin.

Examples

The first example below merges all port geometries into the interconnect: The second example promotes the port geometry of pin FT1, of cell R64. And the third example promotes pin Z, of instance IOA.

    • promote_ports all
    • promote_ports cell R64 pin FT1
    • promote_ports inst IOA pin Z


Extractor Variables


density_check_method

Syntax


setvar density_check_method [diearea|database|perlayer|rectangle|none]

Description

The density_check_method variable selects the method that zx uses to check the wire density of the chip.

Arguments

diearea

Checks the wire density in the area defined by the diearea keyword in the DEF file. It checks the area on all layers. It checks the area by dividing it into a tile size defined by the technology file, usually 50 to 100 microns on a side. This option is recommended for full-chip checking.

database

Checks the wire density in the area defined by the layout database. This area is defined by a leftmost, bottommost point to a rightmost, topmost point. It checks the area on all layers. It checks the area by dividing it into a tile size defined by the technology file, usually 50 to 100 microns on a side. This option is recommended for block-level checking. The default is database.

perlayer

Checks the wire density in the area defined by the extent of routing on each area of a layer. This option is recommended for validating layout accuracy only.

rectangle

Checks the wire density in a rectangular region defined by the command density_check_rectangle.

none

Uses the default method, which is database.

Examples

The following example checks the wire density in an area defined by the diearea keyword in the DEF file:

setvar density_check_method diearea

enable_metal_fill_effects

Syntax


setvar enable_metal_fill_effects [true|false]

Description

The enable_metal_fill_effects variable determines whether zx includes in the extraction results the effects of the metal fill between wires on a layer that was deposited according to the specifications in the DEF file.

Note: zx issues a warning if the DEF file does not contain specifications for metal fill.

Arguments

true

When you set this variable to true, zx includes the effects of metal fill between the wires. The default is true.


If you set the variable enable_metal_fill_effects to true, you must use the variable metal_fill_type to specify the type of metal fill to use, either grounded, which has a fixed electrical charge, or floating, which has no fixed electrical charge. Typically, grounded metal has a higher capacitance.

false

When you set this variable to false, zx does not include the effects of metal fill between the wires.


Examples

In this example, zx does not include the effects of metal fill between the wires in the extraction results:

setvar enable_metal_fill_effects false

The ignore_shorts variable enables zx to either flag or ignore detected shorted nets, as in previous releases. The default setting is true for DEF input, and false for other input. Setting it to true will make zx behave the same as in Version 3.x.

Arguments

Specifies the scale factor by which zx scales the layout. This factor can range from 0.01 to 5. The default is 1.0, indicating that no scaling is performed.

load_optimized_views

Syntax


setvar load_optimized_views [ true | false ]

Description

The load_optimized_views variable specifies that zx load the optimized version of the power-grid views from the cell library. The load_optimized_views variable is used in power-grid analysis flow.

Optimized means that small notches in a VDD port geometry are basically smoothed out. In effect, the extraction for power-grid analysis would typically run faster because it has to deal with less geometry. The side effects would some time cause disconnects or opens typically in tie-hi and/or tie-low types of connection.The default in power-grid analysis flow is true. If optimized view does not exist in the cell library, QX will load the non-optimized one.

Note: The optimization, which is done in LibGen, is only performed for cells which are smaller than the setting of the stdCellSizeLimit LibGen variable.

Arguments

true

When you set this variable to true, zx loads the optimized version of the power-grid views from the cell library. The default is true in a power-grid analysis flow. If an optimized view does not exist in the cell library, zx will load the non-optimized one.
