Path Exception Priorities - Overview

This section describes the path exception priority rules, which are followed by Tempus to determine the effective path exceptions to be applied on a particular path if multiple path exceptions are applied to it. The path exception priority rules are explained as per the path exception command type and various command parameters. The path exception commands are given below:

  • set_false_path
  • set_max_delay
  • set_min_delay
  • set_multicycle_path

Note: The priority rules (as explained in the following sections) are applicable to set_path_adjust_group and group_path commands also.

Priority Rules on the Basis of Path Exception Type

If the types of path exception commands are different, the priority order (in decreasing priority) is as follows:

  1. set_false_path
  2. set_min_delay/set_max_delay
  3. set_multicycle_path

For example, set_false_path -from A is given priority over set_multicycle_path -from A 2.

Priority Rules on the Basis of Path Exception Command Reference Points

The path exception commands use parameters to specify reference points, such as, -from/-through/-to/-clock_from/-clock_to.

If there is more than one exception of a given type, for example the set_multicycle_path command, the path exception that is more specific has higher priority. A path exception has higher priority if it specifies more of the -from/-through/-to parameters. For example, the -from -to options will have priority over the -from option.

Here is an example of path exception priorities for -from/-through/-to parameters:

Priority

Path Exception

1 (highest)

set_multicycle_path -from pins -through pins -to pins

2

set_multicycle_path -from pins -to pins

3

set_multicycle_path -from pins -through pins -to clocks

If the path has the same number of reference points:

  • -from and -to option has priority over the -from option
  • -from option has priority over the -to option
  • -to option has priority over the -through option

For example:

i. set_multicycle_path -from A 2 is given priority over set_multicycle_path -through B 4.

ii. set_false_path -from A is given priority over set_false_path -through B.

2. If there are more than one exceptions of a given type with the same reference point, the path exception that is more specific has a higher priority. A path exception is more specific if it specifies a longer path than the other. For example, the ‘-from -to’ parameters will have a higher priority over -from.

3. If a path exception differs only in terms of number of -through commands specified, the exception with a more constraining value will be honored.

Priority Rules on the Basis of -start/-end (only for set_multicycle_path)

For the set_multicycle_path constraint, if the reference points are the same and both the constraints differ only in -start/-end, the precedence rule is as follows:

  • Command with -start will be higher priority, whereas -end will be lower priority.

Examples of Path Exception Priorities

The following are examples of the path exception priorities for a path starting at A, going through B, and ending with C. The pairs of examples are ordered such that the highest priority constraint in one pair has precedence over the highest priority constraint in the next pair.

  • In the following pair of constraints, the false path overrides the cycle addition for the path from A through B to C. For all other paths from A, the cycle addition applies.
    set_false_path -from A -through B -to C
     set_multicycle_path -from A 2
  • In the following pair, the first constraint is applied (two cycles added) because the -from option has priority over the -to option:
    set_multicycle_path -from A 3
    set_multicycle_path -to C 2
  • In the following pair, the first constraint is applied (two cycles added) because it specifies a -through pin as well as a -to pin:
    set_multicycle_path -through A -to B 3
    set_multicycle_path -to B 2
  • In the following pair, the first constraint is applied (two cycles added) because the -from option has precedence over the -to option:
    set_multicycle_path -from CLKA 3
    set_multicycle_path -to CLKB 2
  • In the following pair, the second constraint is applied because the second constraint overwrites the first one:
    set_multicycle_path -from A 2
    set_multicycle_path -from A 3

Cycle Accounting Rules - Data Checks

The following cycle accounting rules apply in the given below scenarios.

General Single-Cycle Timing

  • When the launch and capture root clock edges align, the Setup capture edge is adjusted so that a full clock cycle is allowed for the path.
  • When launch and capture Setup edges do not align, then the most constraining pair of root edges defines the cycle time  The launch and capture Hold edges are derived from the adjusted Setup edges:
    • Any multi-cycle adjustment to Setup is done before deriving the Hold edges.
    • Two Hold rules are checked and the most constraining  edge pair is used (often they are the same).
      • Data launched from the current cycle at the source cannot be captured by the previous cycle at the target.
      • Data from the next cycle at the source cannot be captured by the current cycle at the target.
  • Hold edges typically align - allowing full CPPR credit - including SI to be given.

Zero-Cycle Timing

The zero-cycle Setup paths launch and capture data off of the same cycle. The zero-cycle Setup paths are obtained from the set_data_check constraint and non-sequential type library checks.

In this case:

  • The adjusted Hold edges mostly yield positive slack.
  • The SI CPPR (50ps) is credited to Setup, but not Hold due to the Hold launch and capture edges not aligning.

Zero-Cycle Timing with Multi-Cycle Adjust

The following command will move the Hold launch back one cycle - making the Hold checks zero-cycle as well:
set_multicycle_path -1 -hold -to [get_ports data] 

The current syntax does not restrict the multi-cycle application to only data-to-data checks.

Since both the Setup and Hold are zero-cycle, both receive the full CPPR credit - including SI.

set_multicycle_path -start 

When the set_multicycle_path -start parameter is used to adjust data-to-data paths, there might be some compatibility issues with third-party software.

You can set the timing_enable_sdc_compatible_data_check_mcp global variable to true to enable checking for SDC compatible data checks. When the -start parameter is specified, the parameter reverses the reference clock by one clock cycle.
