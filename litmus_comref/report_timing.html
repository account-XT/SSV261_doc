Generates a timing report that provides information about the various paths in a design.

The reports typically contain data on the delay through the entire path. The start node and the end node of each path is identified.

The timing report contains the following information:

  • The slack times of the arriving signal at the end node
  • The start node
  • The associated transitions
  • The signal required times and the actual signal arrival times
  • Summary of propagated vs ideal status of launching and capturing clocks
  • Any phase shifts applied when evaluating timing checks
  • Any CPPR values applied to timing check evaluation

The report_timing command output accommodates both the instance pin names and net names in the same column. Since both instance pin names and net names can be long, to save screen space alternating instance pin and net names (depending on whether the row displays gate delay or net delay) are reported in a single column.

When the timing_report_timing_header_detail_info timing attribute is set to extended, the software generates timing reports with additional header information, that includes the following details:

  • Analysis mode - best-case worst-case (BCWC) or on-chip variation (OCV)
  • Active views (displayed only in MMMC mode)
  • Clock re-convergence pessimism (CPPR)
  • Latch slack mode
  • Specified clock propagation value
  • Delay calculation
  • Specified delay calculation engine

When the timing_report_group_based_mode attribute is set to true, the paths are grouped by clock domain. In this mode, the report_timing command will have the following four types of groups:

  • Clock gating group: This is an internal group that reports the clock gating check type paths.
  • Asynchronous group: This is also an internal group that reports the asynchronous check type paths.
  • Groups for all clocks in a design: These are internal groups that are classified on the basis of each reference clock. The paths belonging to each reference clock are reported separately under each clock name’s group. These groups do not honor the clock gating/asynchronous check types. Suppose there are three clocks C1, C2, and C3 in a design, then three groups will be reported for each of these clocks. The endpoint sharing the same reference clock will be part of the same group. In case the endpoint belongs to multiple groups then it will be reported separately in each group.
  • Default group: This is an internal group that reports combinational maximum or minimum delay paths.
  • User-defined groups: These are user-defined path groups that can be created by users with single or multiple constraints. These groups honor all the check types and are reported by default.

By default, the timing_report_group_based_mode attribute is set to false.

Note: This attribute does not honor user-defined path groups, so the paths will still be grouped by different clocks.

The report_timing command supports multi-threaded reporting. You can make the following settings to enable multi-threaded reporting:

set_multi_cpu_usage -localCpu number_of_CPU

set_table_style -no_frame_fix_width [-nosplit]

Note: When the timing_allow_input_delay_on_clock_source attribute is enabled and the set_input_delay command is applied to a clock input, the specified delay value will be considered as the source clock latency for clock paths and as regular data path arrival time for clock source paths.

You can use a one-step method for generating merged MMMC view reports from DMMMC master shell. After running the distribute_views command, you can use the report_timing command to generate reports collectively from all the active distributed views (that is, views available for interactive DMMMC analysis). The merged output report is arranged as per the slack/criticality order across active views.

When the timing_enable_wire_variation attribute is set to true, the timing reports show wire variation details in the below columns:

  • retime_slew_wire_stddev
  • retime_delay_wire_stddev
  • arrival_wire_stddev

For more details on wire variation, refer to the "Wire Variation Analysis" chapter in the Litmus Stylus User Guide.

Parameters

-help

Outputs a brief description that includes type and default information for each report_timing parameter. For a detailed description of the command and all of its parameters, use the man command: man report_timing.

{> | >>} filename

When specified with >, writes the report to the specified file name. If the file already exists, the software will overwrite it.

When specified with >>, writes the report to the specified file name. If the file already exists, the software will concatenate the report at the end of the file.

The filename parameter must be the last argument in the list. The filename and -tcl_list parameters are mutually exclusive; you cannot specify them together.

Note: To write a compressed report, add the .gz extension to the file name.

Note: The last argument specified with the report_timing command is not considered a filename.

Default: Report is displayed on standard output (not saved).

Generates the analysis summary file.

Data_type: string, optional

-begin_end_pair

Reports all the violating paths between unique source and target register pairs. To report other paths, you can specify this parameter with the -max_slack parameter.

The paths are not sorted by slack - paths with the same source pins are reported adjacent to each other.

When specified with the -from, -through, or -to parameter, the software only reports the unique register pair paths that match the path description.

In merged group-based reporting mode (that is, when timing_report_backward_compatible_max_paths_reporting attribute is set to false), the report_timing -begin_end_pair command report_timing –begin_end_pair will always report the paths grouped by path_groups irrespective of timing_report_group_based_mode  attribute setting.

You can use the timing_report_begin_end_pair_max_path_limit attribute to specify the maximum paths limit. When the number of maximum paths to be reported by the -begin_end_pair parameter exceeds the specified limit (default is 200000), a warning message will be displayed. Also, some of the paths may not be reported.

Note: You cannot specify this parameter with the -max_paths, -nworst, -unique_pins, and -min_slack parameters.

Data_type: bool, optional

-check_clocks

Generates reports based on timing paths on the clock network instead of the standard timing to data endpoints. This report includes clock paths that end at the reference end of a check or a clock gating end point.

Default: Data paths and all the other clock paths (for example, a clock path ending at a D pin of a register) are reported.

Data_type: bool, optional
-check_type check_type

Reports only the paths that end at the specified timing check. You can specify the following options:

setup, hold, clock_gating_setup, clock_gating_hold, clock_gating_pulse_width, data_setup, data_hold, recovery, removal, 
pulse_width, clock_period, clock_separation, skew, no_change_setup, no_change_hold, max_delay, and min_delay.

  • The clock style checks are: pulse_width, clock_gating_pulse_width, clock_period, skew, and clock_separation.
  • In setup analysis mode, the reported check types will be:  setup, skew, pulse_width, clock_period, clock_gating_setup, clock_gating_pulse_width, data_setup, recovery, clock_separation, and no_change_setup.
  • In hold analysis mode, the reported check types will be: hold, clock_gating_hold, data_hold, removal, and no_change_hold.

If the software is in simultaneous setup and hold analysis mode, all of the check types listed above will be reported.

When the max_delay and min_delay options are specified, the timing report will display details of timing paths for which the set_max_delay or set_min_delay constraints are defined.

By default, the following checks are reported:

  • setup
  • hold
  • clock_gating_setup
  • clock_gating_hold
  • data_setup
  • data_hold
  • recovery
  • removal
  • no_change_setup
  • no_change_hold

Do not use this parameter with the -unconstrained, -early, or -late parameters.

Note: The report_timing command does not perform skew checks by default.

Data_type: enum, optional

-collection

Returns a collection of timing paths, which is useful for performing Tcl queries on selected timing reports.

To generate a collection of paths analyzed by Path-Based Analysis (PBA), you can use the –retime parameter.

Note: This parameter is not supported in DMMMC mode.

Data_type: bool, optional
–debug {unconstrained | time_borrow | cppr_point | constraint_arc| context | wire_variation | vt_skew}

You can specify the following options for debugging:

  • unconstrained: Determines the reasons for a path to be unconstrained. The report output will list all the applicable arcs/constraints that could not constrain the paths, along with the reasons.
  • time_borrow: Reports time borrowing calculations. Time borrowing is the amount of time borrowed by a previous logic.
  • cppr_point: Reports the CPPR point information for the reported paths.
  • constraint_arc: Reports check arc details, such as, constraint arc delay, constraint pins (along with the related pin slews), skewness, user derate, annotation, and when_cond. 
  • context: Reports the launch and capture path interface timing for each instance and indicates the block port that shows latency in the MIM flow.
  • wire_variation: Reports the corresponding slack shift details at the end of each timing path report.
  • vt_skew: Reports voltage threshold (VT) skew analysis details.

Data_type: string, optional

-derate_summary

Generates a summary table for AOCV derating of launch and capture paths.

Data_type: bool, optional
-fields column_list 

Formats the report according to the specified column_list. The column_list specifies the columns to be displayed in the timing report and the order in which they appear.

The valid field columns are:

adjustment, abs_delay_err, abs_transition_err, annotation, aocv_adj_stages, aocv_derate, aocv_weight, arc, arrival, arrival_mean, arrival_sigma, cell, delay, delay_mean, delay_sigma, direction, edge, fanin, fanout, flags, hpin, incr_delay, instance, instance_location, latch_window, load, module, net, pct_delay_err, pct_slew_err, phase, phys_info, pin, pin_load, pin_location, power_domain, required, retime_delay, retime_delay_mean, retime_delay_sigma, retime_mis_delta, retime_mis_derate, retime_slew, retime_transition_mean, retime_transition_sigma, stage_count, transition, transition_mean, transition_sigma, socv_derate, spice_arrival, spice_delay, spice_slew, stolen, timing_point, total_derate, user_derate, voltage, vt_skew_derate, when_cond, wire_load, wlmodel

For example:

-fields {hpin cell delay required arrival required edge}

See Report Timing Column List for details on the above options.

Few notes:

  • The default net format (with the -net parameter) for the full path will be:
    {hpin edge net cell delay arrival required}
  • The required column will not be displayed, when the -unconstrained parameter is specified.
  • The adjustment column is automatically added to the timing report. To disable this feature you can set the timing_report_generated_clock_info attribute to false. By default this global variable is set to true.
  • You can use a combination of the -fields and -tcl_list parameters to integrate the timing reports into your Tcl scripts. You can use the -from parameter to limit the number of paths reported, and to find specific paths in the design.
  • The -format option cannot be used with the -path_type summary option.
  • You can manage the retiming columns with the timing_report_retime_formatting_mode global variable.
  • If you specify the report_timing -split_delay parameter, then the timing report format will change to:
    {timing_point flags edge cell power_domain fanout transition delay arrival}
  • Informational tags are displayed for reporting additional details with the flags option. For details on the 'Flags' column, refer to the section on Use of Informational Flags.

Default: {timing_point flags arc edge cell power_domain fanout transition delay arrival}

You can use this parameter with the -through and -to parameters for specifying particular paths in the design.

Prints all the hierarchical crossings of an arc under the hpin column.

Data_type: bool, optional

-late | -early

Reports for early paths (hold checks) or late paths (setup checks).

If you specify a check type, setup or hold, with the timing_analysis_check_type attribute, the report_timing command reports the specified check by default.

Note: The -early and -late parameters are not mutually exclusive; you can specify them together.

Data_type: bool, optional
-max_delay float

Specifies the path delay limit for unconstrained paths.

Data_type: string, optional

-max_paths integer

Reports the specified number of worst paths in the design, with maximum of nworst (-nworst parameter) paths to any single endpoint (default 1).

When timing_report_group_based_mode (group-based mode) attribute is set to true, the -max_paths parameter specifies the number of worst paths reported per clock group.

Default: 1

Data_type: int, optional

-max_slack float

Reports only those paths with slack less than the specified maximum slack value.

The -max_slack parameter reports paths that fall within the specified range. A positive slack value indicates that timing was met and a negative slack value indicates a timing violation.

When the -retime_mode exhaustive option is specified, the -max_slack value is set to 0.

The -max_slack parameter cannot be used with the -unconstrained option.

Data_type: string, optional

-min_slack float

Reports only those paths whose slack is greater than the specified minimum slack value.

You can generate a timing report showing paths with slack greater than the specified slack using the -max_paths parameter. For example, to report all paths with slack greater than 2ns, you can use the following command:
min_slack 2.0 -max_paths 1000

In this case the maximum number of paths reported will be 1000.

When the -min_slack parameter is specified, the total numbers of paths processed will be as determined by the -max_paths/-nworst settings and only those paths satisfying the -min_slack criteria will be reported. The software will not process paths beyond the specified max_paths/nworst limit, even if the min_slack criteria is satisfied.

The -min_slack cannot be used with the -unconstrained parameter.

In the below diagram, if -min_slack is 0 and –max_paths 4 –nworst 2 is specified, then only 3 paths will be reported; path with slack value of -1 will be ignored. Here, even if there is another path with slack that is greater than or equal to 2, then it will not be reported because worst max_paths have been processed.

Data_type: string, optional
-nets

Adds a row to the "Timing Point" field column to display the net names.

Note: The -split_delay and -nets parameters can be used together.

Data_type: bool, optional

{-not_through | -not_rise_through | -not_fall_through} object_list

You can specify one of the following options:

  • -not_through: Reports paths that do not traverse through the specified nets, ports, or pins of a cell.

By default, this parameter will be ignored if an object has already been specified. In this case the parameter shows the following behavior:

    • If a collection of all the input ports has been specified (using the all_inputs command), then the report will show paths to the inout part, and paths starting from the internal part of inout will be excluded.
    • If a collection of all the output ports has been specified (using the all_outputs command), then the report will show paths starting from the internal part of inout, and paths ending at inout part will be excluded.
    • If any other collection (not specified with all_inputs or all_outputs command) is specified, then paths to both the ports will not be reported.
  • -not_rise_through: Does not report paths with rise transition.
  • -not_fall_through: Does not report paths with fall transition.

Data_type: string, optional

-nworst integer

Specifies the maximum number of paths which can be reported for a particular endpoint (the total number of paths reported is specified by the -max_paths parameter).

When timing_report_group_based_mode attribute is set to true (group-based mode), the -nworst parameter specifies the maximum number of paths for a particular endpoint per clock group.

You can use the -nworst parameter to report all the checks at an endpoint (or use -check_type) to report a specific check.

Default: 1

Data_type: int, optional
-output_format {text |  csv | gtd | binary}

Generates a detailed timing report in the specified format - text, CSV, GTD, or binary.

Data_type: enum, optional
-path_exceptions {applied | ignored | all}

Includes information of path exceptions applied and considered for the reported path. You can specify the following options:

  • applied: Reports the honored exception on the reported path.
  • ignored: Reports the ignored exceptions on the reported path.
  • all: Reports both applied and ignored set of exceptions on the reported.
    Note: Analyzing all the exceptions for a path will cause increase in runtime.

If multiple from, to, or through pins are specified, the exception report for that path will show only those pins that are part of the current path.

Note: If a path is already unconstrained, then all further path exceptions applied on that particular path will be reported as ignored exceptions.

The –path_exceptions parameter also reports -start/-end options with multi-cycle paths. Without the start or end specification, by default, the setup check is relative to the end clock and the hold check is relative to the start clock. The report_timing –path_exceptions all command will report all the non-default -start/-end specifications.

You cannot use this parameter with the following parameters:

  • -point_to_point
  • -collection
  • -path_type
  • -tcl_list

Also, you cannot use this parameter with block-based SSTA.

Note: Analyzing all the exceptions for a path will increase the runtime.

Data_type: enum, optional
-path_type {endpoint | summary | full | full_clock} 

The -path_type parameter allows you to choose the report format by path type. 

You can specify one of the following options:

  • endpoint: Generates an endpoint report for each path containing the ID, slack, endpoint, and group view. This option generates a very fast report.
  • summary: Generates a summary report for each path consisting of a start point, endpoint, cause, slack, arrival time, required time, and phase. The -fields option does not have any impact on this report format.
  • full: Generates a report that displays the full path with accompanying required time and slack calculation. This is the default path type. You can control the report format using the -fields option.
  • full_clock: If the reported path ends at a timing check, the software reports the full clock path (Other End Path), in addition to the full data path (Timing Path).

Data_type: enum, optional

-point_to_point

Traces the worst delay path between a pair of from-to pins. The paths reported with this parameter only include the cumulative delay of the path. You must specify either the -from or -to parameter, to define the begin and end points of the path.

If you do not specify a -from pin, the standard definition of the begin point of a path applies. If you specify a -from pin, it is treated as the begin point of the path. If you specify a -from pin that is not a valid begin point, the arrival time of the first pin starts from 0.

If you do not specify a -to pin, the standard definition of the end point applies. If you specify a -to pin, it is treated as the end point, and only those paths ending in -to pins are reported. If you specify more than one -to pin, the worst path to each pin-to-pin is reported.

When from-to pins are specified, the software will trace across the trigger arcs and report a path, if there is a clock reaching the CK pin of the trigger arc. However, if there is a begin or end point present between the -from and -to pins, the software will not trace beyond it.

If there is no clock reaching the CK pin of the trigger arc, the software cannot trace across the trigger arc, and no path is reported. Additionally, clock path delay is included only when the clock is in propagated mode.

Note: The -point_to_point and -through parameters are mutually exclusive; you cannot specify them together.

Note: The -point_to_point parameter supports a single -from and -to pin; a list of pins is not supported.

Data_type: bool, optional
-retime_delaycal_pins pin_name

Reports the PBA delay calculation details for timing arcs that fanin to the user-specified to-pin list. 

You can specify multiple pins in the pin list. The delay calculation report will be printed at the end of each timing path for the arcs, which are retimed in that path. The PBA delay calculation report format is similar to the report_delay_calculation output in GBA mode, however, the results may be vary because this output is based on path-based analysis.  

When a cell output pin list is provided, the generated report is for the cell arcs; the cell input pin list generates the net arc report.

This parameter is supported for PBA reporting only.

Data_type: string, optional
-retime_format {manual | retime_compare | retime_replace}

Allows you to set the format of timing reports for retime related fields. You can specify one of the following options:

  • manual: Does not change the report_timing format.
  • retime_compare: If GBA columns are present in the report format, then the corresponding retime options are added. If PBA columns are already present, then there is no change in the format.
  • retime_replace: If GBA columns are present in the report format, then the GBA columns are replaced by the corresponding PBA columns. If PBA columns are already in the report, then there is no change in the format.

Note: The timing report format can be controlled with the timing_report_retime_formatting_mode attribute. The report_timing command setting has precedence over this attribute.

Data_type: enum, optional
-retime_mode {path | exhaustive}

Reanalyzes the specified set of paths using the specified method. You can use one of the following options:

  • path: Reanalyzes the specified set of paths. By default, the software uses the -retime_mode path setting, when the -retime path_slew_propagation option is specified.
  • exhaustive: Enables exhaustive path-based analysis mode. In this mode, the software will exhaustively examine nworst paths of the selected endpoints and then select the true worst path to be reported, based on retimed slacks of all the examined paths.
    When you use this option, reporting can be runtime intensive as the software needs to run an exhaustive search for true worst paths. Therefore, it is recommended to use this option in the later phases of the signoff stage when few violations are left for analysis.

Default: path

Data_type: enum, optional
-retime {aocv | path_slew_propagation | aocv_path_slew_propagation}

Reanalyzes the specified set of paths using path-based analysis (1 path per endpoint).

Note: This feature is not meant to be run on all the paths of a design.

You can specify the following options:

  • aocv: Computes AOCV stage count based on specific paths and applies the AOCV derate values to GBA (graph-based analysis) delays. This option can be used with the following parameters only:
    • -rise/-fall
    • -early/-late
    • -check_type
    • -max_paths
    • -begin_end_pair
    • -from/-from_rise/-from_fall
    • -through/-through_rise/ -through_fall
    • -to/-to_rise/-to_fall
    • -rise/-fall
    • -early/-late
    • -check_type
    • -max_paths
    • -begin_end_pair
    • -from/-from_rise/-from_fall
    • -through/-through_rise/ -through_fall
    • -to/-to_rise/-to_fall
    • -path_exceptions
    • -path_type
    • -max_slack
    • -min_slack
    • -view
    • -derate_summary
    • -nworst
  • path_slew_propagation: Re-evaluates the given set of graph-based analysis (GBA) paths by recalculating the delay values based upon actual propagated slew across the path. In this case the AOCV derates are the ones that are reported during graph-based analysis.

The default timing analysis uses worst-case slew propagation to calculate the delays at each stage. As a result, the timing analysis results can be pessimistic.

Note: This feature should be run only on paths that do not meet the slack margin criteria to help identify the actual failing paths from those that are simply failing due to the conservative delay calculation.

The signal integrity incremental delays can be recomputed for the entire path. You can use the following command to perform path-based signal integrity analysis:

report_timing -retime path_slew_propagation

In the report_timing command output, the Retime Incr Delay column reports recomputed signal integrity delays.

The -retime parameter also supports retiming a collection of paths. This parameter does not retime an already retimed path collection. This feature works in graph-based analysis (GBA) mode for path collections. You can use the following use model to retime collections:

report_timing $collection -retime path_slew_propagation

A path collection stores context dependent data, that is, a delay property in GBA will reflect delay data of the timing path report generated in GBA mode. The same property in PBA will reflect the retime delay data of the timing path report in PBA mode.

The delay column in timing reports is context dependent, when the timing_report_retime_formatting_mode retime_replace attribute is used.

Note: For memory optimization purposes, both the delays will not be stored in the same path collection. You can use this setting for comparison purposes.

  • aocv_path_slew_propagation: Re-evaluates the given set of graph-based analysis (GBA) paths by using path-based AOCV derates and delays using actual path- based propagated slew. This option is a combination of -aocv and -path_slew_propagation options.

For retime report header details, see Retime Analysis Report Header Flags.

Data_type: bool, optional

-through | -through_rise | -through_fall object_list

Reports paths that pass through pin(s) or net(s) specified by the object_list. Any number of -through pins or nets can be specified. Using the -through_rise (or -through_fall) parameters specifies that the paths go through the rising (or falling) edge of the signals on the pins/nets in the object_list.
The object_list is a logical OR function. The resulting path may pass through any of the pins or nets in the -through object_list. To force the report to pass through multiple pins or nets, separate -through statements are needed.

You can use these parameters with the -net parameter.

Data_type: string, optional

-to | -to_rise | -to_fall object_list

Reports paths leading to the pin(s) specified by the object_list. The pins in the object_list can be either pins on the design boundary (ports) or pins on an instance. Only one list of -to pins can be specified per report. Using -to_rise (or -to_fall) specifies that the rising (or falling) edge of the signals on the pins in object_list are at the end of the paths. This parameter also reports on target clock waveform(s).

The -to_rise option applies to endpoints as well as intermediate pins.

Data_type: string, optional

-unconstrained

Reports only the unconstrained paths (paths with no slack). Each signal arriving at the path end node which does not have a matching required time, results in an unconstrained path.

The report_timing command without the -unconstrained parameter reports only constrained paths. If no constrained path is found, there may be unconstrained paths or paths may not exist.

Note: The -min_slack and -max_slack cannot be specified with the -unconstrained parameter.

See Examples for the conditions under which a path is reported as constrained or unconstrained.

Data_type: bool, optional

-unique_pins

Reports paths that pass through unique set of pins.

When this parameter is specified, in group-based mode for a given begin-end point pair, the software will consider all different launch clock paths for reporting unique paths. If for a given begin-end pair and a given capture clock, there is a possibility of different launch clock paths, then each such path will be reported.

Note: Using this parameter may significantly affect runtime and memory usage, if the number of reported paths is high.

-view viewName

Generates report for the specified analysis view. By default, all the active views are analyzed.

You must be in multi-mode multi-corner (MMMC) analysis mode in order to use this parameter. To create a view, you use the create_analysis_view command. To set an active view for analysis, you use the set_analysis_view command.

The report_timing command performs block-based analysis in MMMC mode. By default, the command reports the worst endpoint(s) across all views. You can use the -view parameter to report for individual views.

Default: Reports the worst path to each endpoint across all the analysis views.

Data_type: bool, optional

Group Path Reporting for User-Defined Groups

  • A user-defined group is created with the same name as any of the defined reference clocks and with the same constraint as for the "to" clock. For example, group_path -name CLK -to CLK. 
    In this case only one group named CLK will be displayed in the timing report. This will be the same default group with reference clock CLK. Note that default groups - clock gating and asynchronous checks - will not be honored for this group.
  • A user-defined group is created with the same name as any of the reference clocks but with different constraint as specified for the "to" clock. E.g., group_path -name CLK -from pin1 -to CLK.
    In this case the two groups named CLK will be displayed in the timing report. One group will be the same as the default group with reference clock CLK (which will not honor clock gating or asynchronous checks) and the other will be the user-defined path group with name CLK, which will honor all the checks.

adjustment

Reports generated clock adjustment values. When reporting the detailed path for a generated clock, there are circumstances where the arrival time needs to be adjusted when a create_generated_clock assertion is encountered along the path. The adjustment argument can be used to provide a clearer indication of why a "jump" in the arrival time is seen in the path report.

There are two primary reasons for generated clock-related adjustment to occur.

  • If the timing_enable_generated_clock_edge_based_source_latency attribute is set to false, it is possible that the edge-to-edge requirement specified by the generated clock cannot be satisfied by an existing logic path. This can happen when the source clock to generated clock polarity of the constraint is non-inverting, but the clock path itself constrains an inverting path. In this case, it would be normal to see a half-cycle of adjustment as the software compensates for the path versus constraint mismatch.

By default, the timing reports show the ‘path summary’ and ‘path description’ section. However, the default can be changed by using the report_timing -path_type parameter.

Endpoint Reports

In addition to detailed reports, endpoint reports can also be generated. These reports allow you to include additional endpoint related information that can be useful in debugging or identifying certain issues. For example, an endpoint report can show the number of buffers and inverters on a path. A sample report is as shown:

litmus > report_timing -path_type endpoint
#-------------------------------------------------------
# ID    Slack   Endpoint           Group   View
#       (ns)
#-------------------------------------------------------
   1   -16.913  CRE_IN/p_rg[30]/D  m_clk   def_em_view1
#-------------------------------------------------------

The endpoint reports and detailed reports are mutually exclusive.

report_timing -from latch/D Settings

The report_timing -from [register/latch]/CK command settings can be defined in line with the path reported in full_clock path report (as reported path might be clock->lat/CK->lat/Q->ff2/D). So the report_timing -from CK-pin can be very intuitive.

However, in latch case scenarios where there are multiple D pins on a latch, Litmus supports -from latch/D pin, which is generally used for debug purposes. When propagating across CK->Q arc, the software will perform worst casing across all the D->Q arcs and report the worst path possible. The report_timing -from latch/D2 command can be used to propagate arrival only across D2->Q arc, so that no worst casing occurs. And path report or slack with respect to a particular D pin of latch can be attained.
