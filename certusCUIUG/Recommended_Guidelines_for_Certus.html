Recommended Guidelines for Certus

 Few important guidelines that you need to follow while using the Certus tool. These are mentioned below:

  • Reserve temporary space for Tempus and Certus clients, approximately one-third of the tool's memory capacity, as mentioned in the examples below:
    • If the STA session uses 600GB of memory, reserve 200GB of temporary memory:
      set_distributed_hosts -lsf -resource "mem>600000 rusage\[mem=600000\:tmp=200000\] span\[hosts=1\]" -args { -q xxx -W 100:00 -P tempus -n 16} -time_out 90000
    • If Innovus clients use 80GB memory, reserve 20GB temporary memory:
      set_distributed_hosts -lsf -resource "mem>80000 rusage\[mem=80000\:tmp=20000\] span\[hosts=1\]" -args { -q xxx -W 100:00 -P innovus -n 8} -time_out 90000

If you intend to reuse Tempus client machines for Certus clients, ensure you increase the memory request for the Tempus clients.

  • Ensure that your $PATH environment variable points to the same Innovus version as the Certus client manager session, such as Innovus 26.1x and Certus 26.1x.
  • Ensure that the STA saved sessions in the viewDefinition file have the Quantus technology file defined in create_rc_corner.
  • Ensure that the STA session flat netlist matches the Innovus DB netlist.
    • Any mismatch will indicate don't touch and can impact timing or power closure.
    • Ensure that the netlist is not flattened in STA sessions and Innovus DB.
  • To perform a full flat power reporting on the power view, use the settings below:

distribute_command -views <powerViewName> {report_power}

  • Use the same tool to generate initial SPEF as Certus clients will re-extract parasitic:
    • In case you are generating SPEF on an Innovus DB on a design with ILM, ensure that you add unflatten_ilm before doing extract_rc.
  • Ensure that your Quantus command file does not contain a hard-coded output file name (since the same file name will be executed on each Certus client), and the input file name is accessible from where the Innovus DB is loaded.
    • Provide UPF/CPF in STA sessions when the design has multiple supply voltages.
    • When running power optimization on inter-partitions, the power numbers printed by Certus are for the logic covering the inter-partition zone only and not the full design power.
    • Ensure that the top-only level is always opened for ECO (which is a part of the block restore file) - in case it is not a case of abutted partitions with no logic at the top.
    • The start_distributed_eco_clients command does not prevent the rest of the script from being executed.
      • This command is to start the Innovus distributed clients, but allows the next command to be processed.
      • The purpose is to have opt_signoff start generating ECO DB while all Innovus clients are booted in parallel.
      • Do not perform any netlist change between start_distributed_eco_clients and opt_signoff.
    • In case of an error, you should first check the client manager/client machines, verify the temporary disk space, ensure that there is no CPU overloading situation, and check the current disk space.
      • Check the host-monitor.log file to determine the health of the manager machine and each of the Tempus client machines created for your run.
      • Check the host-monitor-eco-clients.log file to determine the health of the manager machine and each of the Certus client machines created for your run.
    • Ensure to apply the correct views for the Setup analysis and Hold analysis.
      • Adding Hold only views to the Setup active view list may lead to unexpected Setup timing.
    • When having Innovus DBs generated by write_testcase, those cannot be loaded by distributed ECO:
      • Recommended solution is to initially use write_db -lib, which replaces all functions of write_testcase, or you need to load each of those Innovus DBs individually, and save them again with write_db.
    • You cannot use CUI STA with LUI Innovus DB (and vice-versa):
      • You can generate a CUI STA or CUI Innovus DB by loading a LUI DB in CUI and saving it.
    • It is recommended to load each Innovus DB in a standalone Innovus session to check its validity before starting Certus:
      • Run check_place -no_preplaced: Verify that there are no placement violations.
      • Run route_eco: Verify that the tool can converge quickly and does not end with too many DRCs.
    • In case of any error or SEGV that the client manager is reporting from the clients, you must review the client's log files:
      • Tempus Clients: Checks in the directory pointed by distribute_read_db.
      • Certus Clients: Checks in the directory pointed by set_db opt_signoff_distributed_optimization_out_dir xxx.
    • In case you observe significant timing jumps in time_design_signoff after implement_distibuted_eco, do the following:
      • Check the Certus client log files to verify that there is no large instance movement during placement legalization.
      • Ensure that the same parasitic extraction tools or options that were utilized to create the original parasitic data used for the initial STA are enabled.
      • Perform a dry run using the below-mentioned flow to verify that timing does not change during the implementation phase without any ECOs being performed:
        • Load design
        • time_design_signoff
        • implement_distributed_eco -force
        • time_design_signoff

  • To enable custom resource distribution related to CPU and memory configurations for Certus and Tempus clients, use the below settings when running the set_eco_opt_mode -custom_distribution_file <file> command parameter. 

    • For every client, either for Tempus or Certus, or Tempus and Certus, specify the following:
      module=<moduleName> view=<viewName> nCpu=<Number of threads allowed> {<farm distribution instruction>}
    • For client machine sharing, specify the View as view=<viewName> with one (or multiple) Modules, module=<moduleName>
    • For two Certus clients sharing the same machine, specify module=<moduleName> twice on the same line (where the nCPU value is then divided by the number of Certus clients and provided to each Certus client). 
    • Note:
      • When the -custom_distribution_file <file> parameter is specified, Certus ignores the -resource and -args parameters of set_distribute_hosts from the main TCL file and uses only those settings that are defined within <file>. The -time_out parameter of the set_distribute_hosts command will be honored to specify the timeout for a submitted job that will never start. After a timeout, a warning message is displayed.
      • The tool generates an error if any required view or module is not listed in it. This means the user should list all views/modules in this file.
      • The tool first displays the specific error (which can vary in each case, depending on what the user provided incorrectly). However, an informational message is displayed as shown below:
        Usage: The format for each line: module=<blockName> view=<viewName> nCpu=<INT> {bsub ...}. Each line should contain a module, or a view, or both. One or more modules can be specified in a line, but only one view can be specified. The nCpu and {bsub ...} are mandatory and can appear only once in a line. The host launching string should be enclosed within '{' and '}' and should be at the trailing end of a line.
      • This approach allows users the flexibility to assign different clients to different queues.
      • The timeout period is specified using the set_distribute_hosts -time_out command parameter in the main TCL script.
      • In case of CMMMC Tempus clients, the client would take the last occurrence of any of the active views being specified.

Examples:

      • The following command refers to a file (distribution.tcl) where each client requests a separate machine:
        opt_signoff_custom_distribution_file distribution.tcl

        where (distribution.tcl) file includes:

        module=topChip nCpu=16 {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=250000,tmp=50000\] span\[hosts=1\]'} 
        module=small_cpu nCpu=8 {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=150000,tmp=50000\] span\[hosts=1\]'} 
        module=big_GPU nCpu=16 {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 16 -R 'select\[OSREL==EE80\] rusage\[mem=250000,tmp=50000\] span\[hosts=1\]'}
        view=setup_view1 nCpu=16 {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 16 -R 'select\[OSREL==EE80\] rusage\[mem=200000,tmp=100000\] span\[hosts=1\]'}
        view=setup_view2 nCpu=16  {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 16 -R 'select\[OSREL==EE80\] rusage\[mem=200000,tmp=100000\] span\[hosts=1\]'} 
        view=setup_hold1 nCpu=8  {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=200000,tmp=100000\] span\[hosts=1\]'} 
        view=setup_power  nCpu=8  {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=200000,tmp=100000\] span\[hosts=1\]'}         

      • The following command refers to a file (distribution.tcl) that clients use when sharing machines.
        set_eco_opt_mode -custom_distribution_file distribution.tcl

        where (distribution.tcl) file includes:

        module=topChip view=setup_view1  nCpu=16  {bsub -q large -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=450000,tmp=150000\] span\[hosts=1\]'}
        module=small_cpu view=setup_hold1 nCpu=8  {bsub -q large -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=350000,tmp=150000\] span\[hosts=1\]'}
        module=big_GPU view=setup_view2 nCpu=16  {bsub -q large -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 16 -R 'select\[OSREL==EE80\] rusage\[mem=450000,tmp=150000\] span\[hosts=1\]'}
        module=mini_CPU1 module=mini_CPU2 view=setup_view3 nCpu=16  {bsub -q large -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 16 -R 'select\[OSREL==EE80\] rusage\[mem=450000,tmp=150000\] span\[hosts=1\]'}
        view=setup_power  nCpu=8  {bsub -q batch -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 8 -R 'select\[OSREL==EE80\] rusage\[mem=200000,tmp=100000\] span\[hosts=1\]'}
        module=mega_GPU nCpu=32  {bsub -q large -W 100:00 -P SSV:26.1:Certus -o /dev/null -n 32 -R 'select\[OSREL==EE80\] rusage\[mem=350000,tmp=150000\] span\[hosts=1\]'}
