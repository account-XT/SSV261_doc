Promotion Configuration

Constraint Promotion supports a set of configuration controls that specifies how block‑level constraints are processed, prioritized, and resolved during the analysis phase. These configurations ensure constraint ordering and conflict‑resolution. The following figure highlights where user‑defined configuration is applied during promotion analysis:

Configuration consists of two primary settings:

  1. Promotion Priority
  2. Promotion Strategy

Both settings can be applied before initiating constraint promotion.

Promotion Priority

The promotion priority list determines the sequence in which block/instance-level constraints are analyzed. By default, Litmus processes the constraints in alphabetical order of instance names, but you can override this sequence to align with integration priorities or known design dependencies.

Command Usage

set_constraint_promotion_priority [-help] [<obj_list>]

Options

-help

Prints command usage.
<obj_list>

Specifies an ordered list of module names and/or instance names.

Note:

  • Constraint promotion for each constraint type is performed in a block-by-block sequence.
  • If you do not specify a list, the order defaults to alphabetical instance ordering.
  • When a user‑defined list is used, any missing instances are automatically appended to the end of the list so that the final internal sequence covers all instances with associated block constraints.

This ensures that more critical blocks or blocks with complex clocks/exceptions are promoted early.

Promotion Strategy

The promotion strategy determines how conflicts and overlaps are resolved between block-level constraints and top‑level constraints. You can refine the command based on constraint type or object type.

Command Usage

set_constraint_promotion_strategy [-help] -method <enum> \
[-name <string>] [-types <type_list>] [-object_type <obj_type>]

Options

-help Prints out the command usage.
-method <string>

Selects the promotion strategy. (enum, required)

  • Available Methods:

    • block_worst_case (default) — Retains the most conservative constraint.
    • block_priority — Prioritizes block-level constraints over top-level definitions.
    • block_ignore — Ignores the specified constraint class during promotion.
-name <string>

Specifies the strategy name (string, optional)
-types <type_list>

Applies the strategy to one or more specific constraint types. (string, optional)

  • Valid Constraint Types:

    • case_analysis
    • clock (covers create_clock, create_generated_clock)
    • input_delay
    • output_delay
    • clock_latency
    • clock_transition
    • clock_uncertainty
    • clock_gating
    • disable_clock_gating
    • load
    • min_fanout, max_fanout
    • min_trans, max_trans
    • ideal_network
    • false_path
    • multicycle_path
    • min_delay
    • max_delay
    • clock_group
    • slew (covers set_input_transition, set_drive, set_driving_cell)
-object_type <obj_type>

Limits the strategy to specific object types. (enum, optional)

  • Valid Object Types:

    • pin
    • clock
    • net
    • lib_pin
    • promoted_clock
    • mapped_clock


Examples

Override default behavior and use block priority globally:

set_constraint_promotion_strategy -method block_priority

Ignore all slew‑related constraints from blocks:

set_constraint_promotion_strategy -method block_ignore -type slew

Ignore min/max delay constraints specifically on library pins:

set_constraint_promotion_strategy -method block_ignore \
-type "min_delay max_delay" -object_type lib_pin

These examples illustrate how you can customize promotion decisions for fine‑grained control over constraint classes.
