Design Initialization and Constraint Setup

This phase establishes the foundational timing context required before constraint promotion can begin. This phase ensures that all SoC‑level and block‑level inputs are consistently loaded, the design database is fully initialized, and timing constraints are structurally valid. A robust initialization significantly reduces downstream iterations during promotion analysis. The figure below illustrates the Design Initialization step as part of the setup stage:

During this stage, Litmus validates basic design readiness, catches early constraint‑lint issues, and registers block‑level SDCs for later promotion.

Reading Block-Level Constraints

A central task in design initialization is correctly associating block or instance‑specific SDC files with the SoC context. Litmus provides the unified read_hierarchical_constraints command for loading top-level and block-level constraint files.

Command Usage

read_hierarchical_constraints [-help] -top_sdc <string> \
    | { -block_sdc <string> { -block <string> | -instances <string> } }

Options

-help

Prints usage information.
-top_sdc <string>

Specifies top-level SDCs. These must be loaded separately from block‑level SDCs.
-block <string> Specifies the module name when applying the block‑level SDC to all instances of that module.
-block_sdc <string> Specifies the block‑level SDC file(s) to register for promotion.
-instances <string> Associates the block‑level SDC with one or more explicit instances.

Note: 

  • Top‑level and block‑level SDCs cannot be loaded in a single command call. Use multiple commands and load the SoC constraints first using -top_sdc, then load block constraints via -block_sdc.

  • When a module has multiple instances, the -block option allows the command to automatically associate the same block SDC with all corresponding instances.

  • The read_hierarchical_constraints command does not load or apply constraints into the timing database immediately. Instead, it registers and validates the referenced SDC files, and performs checks such as file existence and syntax, so that they can be applied later during the promote_hierarchical_constraints step.

Examples

Load block SDC for a specific instance

read_hierarchical_constraints -block_sdc module_a.sdc -instance instance_a

Load block SDC for all instances of a module

read_hierarchical_constraints -block_sdc module_a.sdc -block module_a

Load multiple block constraints (mixed module‑based and instance‑based)

read_hierarchical_constraints -block_sdc module_a.sdc -block module_a
read_hierarchical_constraints -block_sdc module_b.sdc -instance instance_b
read_hierarchical_constraints -block_sdc module_c.sdc -instance instance_c
