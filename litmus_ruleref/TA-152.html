TA-152

NAME

TA-152

SUMMARY

A latency path from the edge of the master clock at source pin to the edge of generated clock at pin cannot be found. You must modify your create_generated_clock constraint to be consistent with the network topology. The analysis will continue using 0ns source latency for generated clock . For backward compatibility with earlier releases or to remove the edge-to-edge sufficiency checking, you should set the global timing_enable_genclk_edge_based_source_latency to false in the Legacy UI or set the Stylus root attribute timing_enable_generated_clock_edge_based_source_latency to false in the Stylus UI.

DESCRIPTION

One aspect of generated clock handling is which path to select (among all paths from the source to the target) to determine the source latency of the generated clock. At run time, the Common Timing Engine (CTE) checks whether a path being analyzed between a generated clock and its source has the correct cause-effect relationship consistent with the assertion. Paths found to be inconsistent are ignored. Only the paths that are in agreement with the edge relationship are considered for source latency. If there is no such path, zero source latency is used. This selection is done independently for each edge of the generated clock, so the result might be different for each edge. For example, there might be no latency path satisfying the edge relationship for the rise transition (and hence zero source latency), while there might be several candidate paths for the fall transition.

The edge relationship between a generated clock and its source is specified by the create_generated_clock assertion options -divide_by, -multiply_by, -edges and -invert.

For the -divide_by option with a factor which is power of two, both edges of the generated clock are assumed to be generated from the leading edge of the master clock at the source pin. This normally corresponds to the rise transition unless the clock is inverted at the source pin. If the divide factor is not power of two, the assumed relationship is rise-to-rise, fall-to-fall, which means the rise (fall) edge of the master clock maps to the rise (fall) edge of the generated clock.

The -multiply_by option assumes the same rise->rise and fall->fall relationships as -divide_by that are not a power-of-two factor.

For the -edges option, the master clock edges are specified explicitly. Note that the edge numbering always starts with the rise transition being #1, and continues with the next fall being #2 and so on. Even if the clock is inverted at the source pin, #1 is the rise transition. For example, assuming positive polarities, the edge specification {1 4 7} indicates that the relationship is rise-to-rise, fall-to-fall. Similarly, {2 5 8} indicates fall-to-rise, rise-to-fall. On the other hand, {1 3 5} indicates rise-to-rise, rise-to-fall, which is the same as -divide_by 2. Finally, the -invert option reverses the generated clock waveform, so the target edges are swapped during mapping.

Given the edge relationship established from the assertion, if a generated clock edge cannot be produced from the corresponding master clock edge (there is no path satisfying the relationship), CTE issues an error to indicate this. To disable this checking, you can set timing_enable_genclk_edge_based_source_latency to false.

This error indicates the generated clock constraint or logic has some issues and should be recoded so the parent-to-generated clock relationship can be satisfied by the logic. If it is not correct, zero latency will be used for the generated clocks that do not have a satisfiable latency path.
